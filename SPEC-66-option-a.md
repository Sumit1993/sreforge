## 0. One-paragraph scenario intent

A recent "schema cleanup" deploy drops a long-standing composite index that backs the library-list hot path. Local symptoms look like a generic API latency/slowness incident (p99 high across routes, library page spins) — the kind of thing you'd first suspect in the app tier. The **actual cause sits one hop up the service graph, in the database layer**: an Alembic migration in the just-shipped deploy dropped `ix_books_owner_lower_title`, so the default `GET /v1/books` (`WHERE owner_id=? ORDER BY lower(title) LIMIT 25`) reverted from an index-ordered stop-at-25 walk to a full sequential scan + top-N sort over the whole seeded library on every request. Under the read storm this pins the DB/worker CPU and drives p99 past the 300 ms SLO. The fix is to restore the index (roll-forward migration).

This is the **cascading-upstream** shape required by #66: misleading local symptoms at the API/consumer tier, root cause 1 hop up in the DB schema, delivered through the normal deploy path.

## 4. Lever math (the part #66 failed on once — shown explicitly)

**Cost model (single-threaded, `max_parallel_workers_per_gather=0`):**

- **Indexed path** (`ix_books_owner_lower_title` present): `ORDER BY lower(title) LIMIT 25 OFFSET k` → index-ordered scan, descend btree to offset, read 25 rows, stop. Cost ≈ `O(log N + 25 + k)`. **Effectively flat in N** for small offsets. Sub-millisecond query time; p99 dominated by app/serialization overhead, well under 0.3 s even at large N and high RATE.
- **Dropped-index path**: no usable index for `lower(title)` order → **sequential scan of all N `owner_id=1` rows** + **top-N heapsort** (heap size `25+k`) → then LIMIT. Cost ≈ `O(N)` scan + `O(N·log(25+k))` compares, **per request**. Grows linearly in N. Under a constant-arrival-rate storm at RATE r, concurrent requests contend for CPU; per-request latency and queueing rise superlinearly as CPU saturates → p99 crosses 0.3 s.

**Why a bigger working set is required (not optional):** the issue proved index-less seq-scan at **N=150 000, RATE 25–50** is *below* threshold (it is the current healthy baseline of db-pool and #65). So the index-drop's "return to seq-scan" at 150k does **not** breach on its own. The lever is the **gap** between a flat indexed cost and a linear seq-scan cost — widen the working set and the gap widens for free, because the *healthy* (indexed) side barely moves while the *faulted* (seq-scan) side grows.

**Proposed starting calibration (all `# TUNE-ON-CERT`):**

- `SEED_COUNT = 300000` (2× today's 150k). Doubles seq-scan cost; leaves indexed cost ~unchanged.
- `RATE = 50` (matches #65's storm rate; more concurrency than db-pool's 25).
- Storm hits **default title-sort only** (D4), so **100%** of requests pay the sort under fault (vs. ~5/6 under the rotating mixed storm), maximizing CPU pressure per unit RATE.

**What the cold-arm MUST confirm (blocking cert items):**

1. **Fault breaches:** with the index dropped, `BooklogrApiLatencyP99High` enters *firing* within `confirm_fire_timeout_seconds` (240 s) and the p99 PromQL sits above 0.3 s, **sustained**, under the still-active storm. Two independent cold arms, both firing.
2. **Healthy does not breach (headroom / #64 QUALIFIED):** with the index present, the same `SEED_COUNT`/`RATE`/storm keep p99 comfortably below 0.3 s — the `tools/headroom` campaign must write `verify/headroom.md` reading `QUALIFIED`.
3. **Escalation rule if (1) fails:** raise `SEED_COUNT` first (400k → 500k), then `RATE` (65 → 80). Because indexed cost is ~flat, raising `SEED_COUNT` is the safe dial — it grows the faulted side without endangering the healthy side. Re-run the headroom campaign after every bump.
4. **Escalation rule if (2) fails** (healthy also breaches — unlikely, would mean even the indexed path can't keep up): lower `RATE`, or confirm the index is actually being used (`EXPLAIN (ANALYZE)` on the exact query should show `Index Scan using ix_books_owner_lower_title`, not `Seq Scan`). If the planner refuses the index at the chosen N, that is a design-blocking finding — report it, do not paper over it.

Record the final `SEED_COUNT`/`RATE` and both measured p99 values (healthy + faulted) into `verify/headroom.md` and `verify/acceptance.json` at cert time. Until then they stay `# TUNE-ON-CERT` in `scenario.env` and the docs.

Revises: 0246901434a1
Create Date: 2025-08-04 10:12:44.000000

"""
from alembic import op
import sqlalchemy as sa

branch_labels = None

> ```python
> op.create_index(
>     'ix_books_owner_lower_title',
>     'books',
>     ['owner_id', sa.text('lower(title)')],
>     unique=False,
> )
> ```

## 6. Alembic fix-redeploy gotcha (call out prominently in reference-fix.md)

The arm applies the drop migration → live DB `alembic_version = e2a9d4c1b6f8` (drop rev). The fix redeploys and runs `flask db upgrade`:

- **Roll-forward fix (correct):** adds `f5b1c8e3a7d2` with `down_revision = e2a9d4c1b6f8`. `flask db upgrade` sees current=drop rev, walks forward one step, re-creates the index. Entrypoint proceeds → gunicorn starts → index restored → p99 clears. 
- **Naive file-revert (fails closed):** if a fix deletes the drop-migration file while the DB is still at the drop revision, alembic can't locate the current revision → `flask db upgrade` errors → `entrypoint.sh` hits `FATAL … exit 1` → container never starts → no redeploy → `ci_green`/`alert_cleared` never satisfied → run fails. This is realistic and honest (you don't un-commit prod history; you roll forward). reference-fix.md must state it so graders understand why a revert-style diff can score 0.

This gotcha is also why the mitigation oracle's fail-closed "container not redeployed after fix" short-circuit is load-bearing here.
